# ADR-0003：选择 LangGraph 承载持久化状态与人工介入

- 状态：已接受
- 日期：2026-09-05
- 相关：PRD §6.3、§5.3、§5.4

## 背景

本项目的核心能力之一是：Agent 在需要用户确认或人工审批时**暂停**，
等外部决策回来后**从原处恢复**，而不是重开会话。
进程崩溃后也要能从最近状态恢复。

这要求一个具备持久化 checkpoint + 中断/恢复语义的编排层。

## 决策

**用 LangGraph 作为唯一编排层，配 `langgraph-checkpoint-postgres` 做持久化。**

LangChain 只在文档加载 / 切分 / embedding 封装上局部使用，不使用它的 chain 抽象。

## 理由

我们需要的四件事，LangGraph 一次性提供：

| 需求 | LangGraph 提供 |
|---|---|
| 强类型状态贯穿多节点 | `State` + reducer |
| 状态持久化到 Postgres | 官方 checkpointer |
| 在任意节点暂停等待外部输入 | `interrupt` |
| 从暂停点精确恢复 | `thread_id` + checkpoint 恢复 |

自研等价物意味着要自己实现 checkpoint 序列化、版本管理、并发写入与恢复语义——
这是整个项目里最不值得自己造的轮子。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 自研状态机 + 自己写 checkpointer | 成本高、易错，且不是本项目要展示的能力 |
| Temporal / Airflow 等工作流引擎 | 面向长任务编排，与 LLM 的 token 流式交互不匹配，运维成本过高 |
| 纯 FastAPI + 数据库状态字段 | 恢复语义要手写；"从第 N 个节点继续"难以正确实现 |

## 后果

**正面**：HITL 与崩溃恢复几乎是免费得到的；`thread_id` 天然成为会话主键。

**负面**：绑定了一个仍在快速演进的框架，版本升级可能有破坏性变更——
用锁定版本 + 评估回归门禁来控制。

**重要衍生约束**：checkpoint 恢复意味着节点**会被重放**。
因此任何副作用必须与状态变更在同一事务中记账（本版靠数据库唯一约束，
接入真实外部服务后必须上 transactional outbox，见 ADR-0005 与 PRD §17）。
