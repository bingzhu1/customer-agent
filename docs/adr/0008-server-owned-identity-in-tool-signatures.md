# ADR-0008：工具签名中不暴露身份字段

- 状态：已接受
- 日期：2026-09-05
- 相关：PRD §4.2 FR-208、§9.6、§9.8

## 背景

常见做法是把 `user_id` 放进 prompt 或工具参数，然后在工具内部校验"这个订单是否属于这个用户"。
这个做法有校验，看起来安全。

但它的安全性建立在"模型会传对 user_id"之上。模型被注入或幻觉时，
攻击的**语法路径是存在的**，只是被一道校验挡住。

## 决策

**工具签名中不得出现 `user_id` / `tenant_id`。**

```
✗ get_order(user_id, order_id)
✓ get_order(order_id)          身份从 AuthContext 依赖注入
```

身份链路固定为：

```
JWT → middleware → AuthContext{user_id, tenant_id, roles}
    → 依赖注入到 Service/Repository
    → Repository 自动附加 WHERE user_id = ctx.user_id
```

请求体中出现的任何身份字段一律**忽略**，不报错也不采信。

## 理由

这是把"攻击被拦截"升级为"**攻击不可表达**"。

LLM 连"查询别人订单"这句话都拼不出来——它能提供的只有 `order_id`，
身份永远来自服务端。归属校验依然保留（防止 id 猜测），但攻击面小一个数量级。

配套的存在性保护：他人订单与不存在订单**返回完全相同的 `not_found`**，
避免通过枚举 id 探测数据是否存在。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 工具带 user_id + 内部校验 | 攻击路径存在，安全性依赖单点校验不被绕过 |
| 在 system prompt 中声明"只能查用户 X 的数据" | prompt 是可被注入改写的，不构成安全边界 |
| 每次调用前让 LLM 复述身份 | 增加 token、增加失败模式，不增加安全性 |

## 后果

**正面**：越权在语法层面不可表达；工具 schema 更简洁，模型更容易用对；
评估中的授权测试可以做成硬门槛。

**负面**：工具无法表达"管理员代查他人订单"这类场景——
这类需求要走独立的、带角色校验的管理接口，不走 Agent 通道。这是有意的。

## 强制手段

- 自动化检查：工具 schema 中不得出现身份字段名
- 代码审查红线（CLAUDE.md 红线 1）
- 评估集 Security 类 10 条，`authorization violation` 必须 = 0
