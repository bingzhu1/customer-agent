# ADR-0006：Policy YAML 作为唯一事实来源，RAG 语料由其生成

- 状态：已接受
- 日期：2026-09-05
- 相关：PRD §9.2、§11

## 背景

系统里存在两份"政策"：

1. RAG 知识库中的政策文档（Agent 用来回答用户）
2. 确定性策略引擎中的规则（系统用来决定能不能执行）

**这两份一定会漂移。** 典型生产事故是：Agent 引用政策告诉用户"你符合退款条件"，
引擎却拒绝执行——用户看到的是"AI 骗我"。

## 决策

**`policies/*.yaml` 是唯一事实来源，RAG 语料由它生成。**

每条规则包含结构化条件（供引擎求值）和 `human_text`（唯一的人类可读表述）。
ingestion 从 YAML 生成 chunk，chunk 的 metadata 带 `policy_id` / `policy_version` / `anchor`。

配套两条强制校验：

1. **引用后置校验**：回答中每个 `policy_id` 必须存在于本轮检索结果中
2. **引用—执行一致性校验**：同轮既有判定又有回答时，二者的
   `policy_id` 与 `policy_version` 必须一致——评估中此项**必须为 100%**

## 理由

"维护两份 + CI 校验一致性"听起来更灵活，但实际上：

- 校验只能发现不一致，不能防止不一致
- 人类文档的措辞变化很难自动比对语义
- 版本对齐要靠纪律，纪律会失效

**生成**比**校验**更简单也更可靠，因此直接列为 P0，而不是放到 P1。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 人工维护 markdown + 独立规则表 | 必然漂移 |
| 只有 markdown，规则由 LLM 从文档推断 | 回到了 ADR-0005 否决的路 |
| 只有规则表，回答直接渲染规则 | 人类可读性差，客服话术生硬 |

## 后果

**正面**：政策变更只改一处；引用与执行天然对齐；版本号贯穿判定、引用、审计三处。

**负面**：`human_text` 的写作被约束在 YAML 里，长篇 FAQ 需要单独的文档通道
（本版按标题切分处理）；策略变更后需要重新 embedding。

## 复审条件

若政策文档演变为需要复杂排版的长文（多级条款、表格、示例），
需要重新设计 ingestion，但"单一事实来源"这条原则不变。
