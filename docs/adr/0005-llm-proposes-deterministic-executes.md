# ADR-0005：LLM 提议，确定性代码执行

- 状态：已接受
- 日期：2026-09-05
- 相关：PRD §9.1、§9.6、§5.3

## 背景

客服 Agent 必须能执行写操作（退款）。问题是：谁来决定"这次到底能不能退"。

最省事的做法是把政策写进 prompt，让模型自己判断并调用 `request_refund`。

## 决策

**LLM 只能产出 `ActionProposal`，绝不直接执行写操作。**

执行链路固定为：

```
LLM 提议 → 确定性策略引擎判定 → 待执行动作落库
        → 用户确认 / 人工审批 → 幂等执行 → 审计
```

策略引擎是纯函数：输入是从业务库**实时查询**的 typed facts，
输出是 `PolicyVerdict{effect, policy_id, policy_version, reason_code}`。

## 理由

让 LLM 直接决定退款，有四个层面的问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 不可审计 | 出事只能说"模型当时这么判断"，无法回答依据哪条规则哪个版本 |
| 2 | 不可测试 | 策略正确性变成概率问题，无法写断言，无法回归 |
| 3 | 可被注入 | 政策若在 prompt 中，用户输入 / 订单备注 / 工单正文都能改写它 |
| 4 | 不可变更 | 改政策要重调 prompt 并重跑全量评估；改规则表只需一行且带版本号 |

## 备选方案

| 方案 | 否决理由 |
|---|---|
| LLM 直接调用写工具 | 上述四条 |
| LLM 判定 + 事后校验 | 校验失败时用户已经看到了"可以退"的答复，体验与信任双输 |
| 全部写操作转人工 | 失去自动化价值，且无法展示幂等与确认流的设计 |

## 后果

**正面**：策略正确性可用不依赖 LLM 的参数化单测覆盖；
审计链完整；政策变更成本极低。

**负面**：多一次数据库查询与一个判定节点，延迟略增（可接受）；
策略规则表需要单独维护（由 ADR-0006 解决同源问题）。

## 衍生约束

- 幂等键由数据库唯一约束保证，**不允许**用"先 SELECT 再 INSERT"替代
- 本版 `RefundService` 是模拟实现；接入真实支付时**必须同时启用 transactional outbox**，
  否则 checkpoint 重放会导致重复扣款
