# ADR-0001：单 PostgreSQL 双 schema，不引入 MySQL

- 状态：已接受
- 日期：2026-09-05
- 相关：PRD §7

## 背景

真实企业里业务数据（订单、用户、支付）通常已存在于一个既有数据库（常见是 MySQL），
Agent 平台自己的状态（会话、checkpoint、审计、记忆、向量）则是新建的。
一个"工业级"架构因此常被画成 MySQL + PostgreSQL 双库。

问题是：我们这个项目里，两个库都是我们自己建的，业务库也是我们自己造的模拟数据。

## 决策

**只用一个 PostgreSQL，内部划分两个 schema：**

- `biz` —— 扮演"已存在的企业业务系统"，权威业务事实
- `agent` —— Agent 平台自己的状态

配套三条约束：

1. `biz` 只能通过 `BizRepository` 访问
2. 禁止跨 schema JOIN（SQL 中不得同时出现 `biz.` 与 `agent.` 表）
3. 两侧不共享事务边界，跨侧一致性按最终一致处理

## 理由

`biz` 与 `agent` 之间的真正边界是**所有权与信任边界**，不是存储引擎边界。
双 schema + 独立 Repository + 禁止跨库 JOIN，已经完整表达了这条边界，
而且把 `BizRepository` 换成真实 MySQL 实现时**只需替换一个实现类**。

多维护一个数据库带来的是：compose 更复杂、迁移工具翻倍、事务讨论负担、
本地起服务更慢——换不到任何架构收益。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| MySQL(biz) + PostgreSQL(agent) | 为技术栈丰富度制造复杂度，收益为零 |
| 单 schema 全放一起 | 丢掉了信任边界，无法表达"业务系统不归我管"这个真实约束 |
| SQLite | 无法演示迁移、并发、pgvector |

## 后果

**正面**：本地一条命令起全栈；迁移工具只有一套；边界仍然清晰可讲。

**负面**：面试时需要主动解释"为什么不是两个库"——但这恰好是一个加分回答。
另外要靠自动化检查来保证禁止跨 schema JOIN，而不是靠物理隔离强制。

## 复审条件

出现以下任一情况时重新讨论：业务库不归本团队管；跨团队 schema ownership；
合规要求物理隔离；业务库负载不能被 Agent 查询影响。
