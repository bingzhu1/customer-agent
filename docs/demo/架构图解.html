客服 Agent 架构图解

一句话总纲：模型只负责"听懂"和"提议"，判定、执行、记账全部交给确定性代码。下面每一张图、每一层设计，都是这句话的落点。

LLM 在做主（Sonnet 5 / Haiku 4.5）确定性代码在做主（纯函数、SQL、状态机）身份 AuthContext红线 / 权威事实

为什么要这样分工

把客服 Agent 想成一家银行柜台。前台的接待员（LLM）负责听懂客户在说什么、把诉求填成表单。但钱能不能退、退多少、给谁退，是后台的规章制度和账本（确定性代码 + 数据库）说了算。接待员再会说话，也拿不到金库钥匙。

这么做的原因很直接：模型的输出有随机性，同一版本跑两次 eval 结果都可能不同。安全类的判定不能接受随机，所以凡是"越权、注入、退款资格、金额上限"这类问题，都必须有一条不依赖模型的确定性路径兜底。

同一套 54 条 golden 用例，三个版本的实测结果：

版本加了什么success越权次数注入抵抗policy 类引用与执行一致
V0 裸模型只有 LLM，没工具没检索1 / 54750%0 / 10n/a
V1 加工具6 个只读工具 + Repository 强制身份过滤 + 决策矩阵19 / 540100%2 / 10n/a

图一：分层架构，一次请求走过哪些层

从左到右是一次请求的路径。上面那条蓝色的带子是身份：从 JWT 解出 user_id 之后，它沿着最外层往右传，直接注入到 Repository，中间的 LLM 节点一眼都看不到它。

每一层只做一件事，CLAUDE.md 里写死了禁止事项：路由不写业务逻辑，图不直接碰数据库，工具不含业务规则，引擎不做任何 IO。这样每一层都能单独测，也能单独换。

图二：一轮对话，七个节点谁在做主

LangGraph 图是一条直线，没有条件边。这一点是刻意的：流程本身不该由模型决定。如果让模型自己决定"要不要去查策略"，那它就有可能跳过检查。现在 policy_gate 和 decide 每一轮都必然执行，模型绕不过去。

用一句人话说每个节点

  1. ingest 开工准备把上一轮留下的 CaseFacts（这次会话已确认的订单号、引用过的策略）从库里拿出来，顺手查一下长期记忆有没有和这句话相关的偏好。工具调用次数归零。
  2. understand 听懂唯一的任务是把用户的话填成一张表：意图是查订单还是退款、提到了哪个订单号、是不是要人工、是不是在自称管理员、是不是在要别人的数据。它明确被告知"你无权决定能不能退款"。用户说"那个订单能退吗"没有订单号时，由代码从 CaseFacts 补最近一个，不让模型猜。
  3. act 查事实按意图调工具。工具签名里没有 user_id，身份在构造工具时就已注入，所以"查别人的订单"在语法上写不出来。他人的订单和不存在的订单都返回 None，调用方无从区分，防止用枚举订单号探测数据存在性。同时扫描用户原话和订单备注里的注入关键词。
  4. policy_gate 对规章把订单的类别、状态、签收天数、会员等级从数据库里现查出来拼成 PolicyFacts，交给策略引擎和 YAML 规则比对。用户说"我没用过"不算数，只认库里的 item_condition。产出一个 verdict：允许、拒绝、需人工、无规则。
  5. decide 定终态16 条规则按顺序过一遍，第一条命中的就是结果。顺序就是优先级：先看归属不符、疑似注入、自称高权限这三条安全规则，再看客户要人工、情绪激烈，再看策略 verdict，再看金额是否超自动上限，最后才是检索置信度。终态只有 6 种：ANSWER、DENY、REQUIRE_CONFIRMATION、REQUIRE_HUMAN、REQUEST_INFO、DEGRADE。
  6. respond 说人话拒绝、转人工、请补信息、待确认这些分支逐字用模板，模型不许改写。这样"他人订单"和"不存在订单"两种情况回复一模一样，注入原文也不会被复述回去。只有真要回答内容的 ANSWER 分支才调模型，此时它能用的事实全在 prompt 里，引用由代码给定，编不出条款编号。
  7. persist 记账把这轮判定依据的策略写进 CaseFacts 落库，再把这轮对话丢进后台队列去抽长期记忆。放在最后是因为写记忆失败不能影响已经生成好的回复。

图三：退款写路径，提议、确认、执行三段分开

退款是唯一的写操作，也是最容易出事的地方。设计原则是模型只能产出提议，提议落库有幂等键，用户点确认才执行，执行前再校验一遍归属、过期和状态。

还没做到的形态：PRD 原本设计用 LangGraph 的 interrupt 暂停在图里、resume 从原处恢复。现在是 ChatService 同事务落提议，确认走独立 REST 接口。效果一样，但"崩溃后从第 N 个节点续上"这件事还没有。

LangGraph 用了什么、没用什么

先澄清一个名字：项目没有用 LangChain。依赖里只有 langgraph，源码里没有 chain、agent executor 或 ReAct 循环，langchain-core 只是被 langgraph 拖进来的传递依赖。

为什么选 LangGraph 而不是别的？ADR-0003 的理由是需要三件事：强类型状态贯穿多节点、状态持久化到 Postgres、能在任意节点暂停等外部输入再从原处恢复。ADR-0002 否决了多 Agent（Router 加四个专职 Agent）和自由循环的 ReAct，因为单业务域、单权限边界、工具个位数，拆分收益为零，而固定流程能保证 policy_gate 必然执行。ADR-0004 否决了 PydanticAI，因为它不提供持久化中断与恢复。

能力设计（ADR-0003）现状差在哪
强类型状态 + 节点隔离StateGraph + TypedDict已用AgentState 明确标注每个字段由谁写
线性流程，无条件边7 节点直线已用模型无法跳过任何检查
checkpoint 持久化Postgres checkpointerMemorySaver进程内保存，重启即丢；跨轮状态实际由 CaseFacts 落库承载
interrupt / resume确认时在图里暂停未用确认走 REST 接口 + ActionService，见图三
崩溃恢复同一 thread_id 续上未做Phase 1 DoD 之一，checkpoint 重放会重复副作用，真接支付前需 outbox

所以现阶段 LangGraph 的实际价值是"把七个步骤钉死顺序、状态强类型、每个节点可单测"。持久化与恢复是它被选中的理由，但还没兑现。冲刺时把它明确推后了。

图四：RAG，从策略 YAML 到带引用的回答

RAG 这里有一个和一般项目不一样的地方：语料不是人写的文档，是从策略 YAML 生成的。同一份 YAML 既给策略引擎判定用，又生成检索语料。这保证了"回答里引用的条款"和"执行退款依据的条款"永远同一个版本，这项一致性在 V3 实测是 12/12。

τ 是怎么定的，以及为什么定不准

PRD 规定 τ 不许拍脑袋。标定脚本用 golden 里的 RAG 用例跑检索，记录每条的最高分和人工标注的"真有答案吗"。两个发现值得讲：

  • 查询改写把正负样本的间隔从 0.06 拉大到 0.16，2.5 倍。口语里的寒暄和句式本身带语义，会把"未覆盖主题"的分数抬起来；改成主题词后负样本掉得更快。结论是 τ 必须和改写一起标，两者是一套。
  • 负样本只有 1 条，机械规则"τ_low 取负样本 95 分位"在 n=1 时等于那一个点，会把唯一的负样本自己判错。所以最终取了区间中点留余量：0.48 / 0.57。
  • RAG-008 怎么调都救不回来："金卡积分能抵现吗"与会员权益条款相似度 0.657，但那条只说了"积分 1.5 倍"，没说怎么用。余弦相似度衡量的是主题相关，不是答案包含。这是向量检索的本质局限，不是阈值问题。

三处配置不一致，需要统一：ADR-0007 定的 τ_high 是 0.57，.env 里是 0.50，settings 默认值还是占位的 0.30 / 0.60。另外跑一次 make test 会把主库的策略向量覆盖成假向量，demo 的真 RAG 会立刻失效，测完要重新灌库。

RAG 没做的部分：BM25 混合检索与 RRF 融合、cross-encoder 重排、Haiku 查询改写接线（函数写好了，图里用的是确定性兜底）、引用校验失败后的重生成循环（校验纯函数有，循环没接）。这些在 PRD §11 里都标了 P1 / P2 优先级，冲刺时明确推后。

SQL：一个库、两个 schema、一条铁律

只有一个 Postgres 实例，里面两个 schema。ADR-0001 的理由：一个库两套 schema 足够演示边界，又不用为 demo 起两个数据库。

schema表谁拥有作用
biz
模拟企业业务系统		users · orders · order_items · shipments · payments · refunds · ticketsseed 脚本全量拥有，每次重灌清空唯一权威事实。判归属、判资格、判金额只能从这里查
agent
Agent 平台状态		threads · messages · case_state · user_memory · memory_embeddings · policy_chunks · agent_actions · audit_log · human_review · eval 结果表Agent 自己写会话、记忆、向量、待确认动作、审计

边界靠什么守住

  • Repository 强制 scope。每条查询由本层拼上 WHERE user_id = ctx.user_id，方法签名里没有身份参数，调用方跳不过。物流、退款、支付表自身没有 user_id，就必须 join 订单表再过滤。
  • 他人与不存在返回同一个 None。路由统一翻成 404，不区分两者。否则攻击者可以用"404 还是 403"探测某个订单号是否存在。
  • 禁止跨 schema JOIN。一条 SQL 里不得同时出现 biz 表与 agent 表。agent 表也不向 biz 建外键，threads.user_id 只是普通整数。两套系统不绑死，将来业务库换成 MySQL 或内部 API 时只换 Repository。
  • UNIQUE(idempotency_key) 是防重复退款的最后一道闸。见图三。

技术栈：SQLAlchemy 2 + psycopg3，Alembic 三个迁移（biz 初始表、agent 平台表、pgvector 列与 HNSW 索引）。向量检索用原生 SQL 写，因为 ORM 表达不了 <=> 距离算子。没做的：RLS 多租户、真实业务库对接、transactional outbox、LangGraph 的 checkpoint 表。

图五：记忆五层，权威性从上到下递减

这个项目里"记忆"不是一个东西，是五个。PRD 把它们按权威性排了序，一句话区分：① 事实 ② 这次对话发生了什么 ③ 这个案子进行到哪 ④ 这个人是什么样的人（仅供参考）⑤ 公司的规定是什么。

短期记忆：不是塞历史消息，是 CaseFacts

一般 chatbot 的"短期记忆"是把前几轮对话原文塞进 prompt。这个项目没这么做。它用一个强类型结构 CaseFacts 记"这次会话已经确认过的事"：涉及了哪些订单号、哪些工单号、提过哪些金额及其来源字段、引用过哪些策略、有没有待确认的动作。

关键在于谁能写。只有三个纯函数：从工具结果按白名单键取值、从策略 verdict 记引用的条款、从已登记的动作记状态。刻意没有 apply_text 这类入口，模型想往里写东西，类型上就无路可走。订单备注、工单正文这些用户可写的字段也不在白名单里。它每轮落到 case_state 表，跨轮跨进程都能续上。

它的实际作用：用户第二轮说"那个订单能退吗"，understand 节点从 CaseFacts 取最近一个已确认的订单号补上，而不是让模型猜，更不是从长期记忆里"回忆"。另一个确定性来源是 biz.refunds：订单已有成功退款时，act 节点算出 prior_refund_exists，decide 走矩阵规则 11 幂等重放，不再产生新提议。这是 9 月 5 日修掉"同一订单跨会话退两次"之后加的第二道闸。

坦白两点没做完的：叙述压缩模块已写好（Haiku 摘要、保留最近 6 条、8000 token 触发、CaseFacts 不参与），但图里没有 compress 节点，没接线。respond 的 prompt 现在只有本轮用户原话加事实，历史消息存进 messages 表但没喂给模型。所以多轮连贯性完全靠 CaseFacts 的实体承接，闲聊式的上下文接不住。

长期记忆：非权威、异步、可删除

persist 节点把本轮对话投进进程内的单线程队列后立即返回，热路径不等它。后台用 Haiku 抽取五类东西：语言偏好、渠道偏好、沟通风格、反复出现的投诉主题、未闭环的历史投诉指代。四道过滤：类别白名单外的丢，命中"可退款、免审批、VIP"之类正则的丢，置信度低于 0.6 的丢，同一 key 再写就覆盖并版本加一。

写入带来源 thread、置信度、180 天 TTL、软删除标记，向量与 RAG 共用同一套 pgvector。检索时按 user_id 硬隔离，取相似度 top 5，其中 language_preference 固定注入。命中后带"[非权威提示，可能过时或有误]"前缀只进 respond 的 prompt。这段前缀是固定措辞，不参数化，它是安全标注不是文案。

记忆能改的东西有一个清楚的例子：回复语言。判定是确定性代码，本轮明确要求（"以后用英文回答"）最高优先，其次记忆里的 language_preference，都没有就中文。拒绝、转人工这些模板分支有 22 组英文骨架跟着切。记忆在这里只决定用哪种语言说，不碰判定，这是红线 3 允许的范围。

为什么用进程内线程池而不是任务表加独立 worker？因为长期记忆是非权威的。进程重启丢一条"用户偏好短信通知"，下次会话再抽一次就有了，且它影响不了任何判定。真正"绝不能丢"的是退款这类外部副作用，那条路走 outbox，和这里不是一回事。

真正上线还缺什么

PRD §17 列了 12 条故意没做的事。最关键的一条：接真实支付时必须同时上 transactional outbox，因为 checkpoint 恢复会重放节点，现在只靠数据库唯一约束防重复扣款。其余包括多实例部署（限流与锁迁 Redis）、多租户（tenant_id 进所有查询，考虑 RLS）、密钥管理、数据保留合规、对接 Zendesk 类工单系统、OpenTelemetry、语料超 5000 chunk 后评估 HNSW 参数与重排。

三条红线，违反直接拒绝合入

1 身份与授权永不经过 LLM2 写操作永不由 LLM 直接触发3 记忆永不进入授权与策略判断

三条红线在代码里各有一个落点：工具签名里没有 user_id（红线 1，图一蓝色带子）；LLM 只能产出提议，执行要过策略引擎、用户确认、幂等键（红线 2，图三）；policy_gate 与 decide 的输入类型里根本没有 memory 字段，投毒测试在 CI 里拦截（红线 3，图五那条红线）。共同的思路是让越权不可表达，而不是靠 prompt 里写"请不要"。
